# Barb’s Table

Barb’s Table is a recipe catalog for our family's recipes. Anyone can browse and search it; approved members add recipes in three ways, all normalized to one recipe shape: photos of a written or printed recipe, a pasted recipe URL, or manual entry. Members request access, are invited by the admin, and sign in with a passkey or an emailed code.

## Stack

- [Next.js 16](https://nextjs.org/docs) (App Router, TypeScript) on Vercel, at [barbtable.com](https://barbtable.com), whose DNS is in Route 53
- [Neon](https://neon.com/docs) Postgres via the Vercel Marketplace, which also powers search, through [Drizzle ORM](https://orm.drizzle.team/docs/overview)
- [Vercel Blob](https://vercel.com/docs/vercel-blob) (private store) for recipe images
- The [AI SDK](https://ai-sdk.dev/docs) through the [Vercel AI Gateway](https://vercel.com/docs/ai-gateway) for reading recipe photos and pages into drafts
- [shadcn/ui](https://ui.shadcn.com/docs) on [Base UI](https://base-ui.com) primitives, with Tailwind CSS v4 tokens
- [Better Auth](https://www.better-auth.com/docs) with email codes and passkeys, sessions in Postgres
- [Resend](https://resend.com/docs) for email, through the Vercel Marketplace, sending as `Barb’s Table <recipes@mail.barbtable.com>`
- [Vercel BotID](https://vercel.com/docs/botid) on the access request form and sign-in code requests

## Development

Requires Node 24, [pnpm](https://pnpm.io/installation), and the [Vercel CLI](https://vercel.com/docs/cli).

```bash
pnpm install
pnpm exec playwright install --only-shell chromium firefox webkit   # once, the browsers pnpm test:unit and pnpm test:e2e run in
vercel link       # once, connects this checkout to the Vercel project
vercel env pull   # writes .env.local; the Blob and AI SDKs renew its 12-hour OIDC token with your CLI login
pnpm db:migrate && pnpm db:bootstrap && pnpm db:seed   # once, and after pulling new migrations
pnpm dev
```

Sign in at [localhost:3000/sign-in](http://localhost:3000/sign-in) with a code emailed to `ADMIN_EMAIL`, the account `pnpm db:bootstrap` makes an admin. Development sends real email through Resend.

pnpm applies `patches/next@16.4.2.patch` to Next's `"use cache"` wrapper and its dev server's manifest writes as it installs; the patch's header says what each part fixes and when to remove it. Changing Next's version fails `pnpm install` until the patch is re-made against the new version or removed, and re-making it with `pnpm patch` drops the header, so carry that over.

The end-to-end suites in `e2e/` drive that dev server on Neon `develop`, in three Playwright projects: iPhone (WebKit), Pixel (Chromium), and desktop Chromium. `pnpm test:e2e` uses the `pnpm dev` already serving this checkout on `localhost:3000`, the one host where sessions are read, or starts one for the run and stops it after (restart a running one after changing dependencies, since the suites reuse it); run `pnpm db:seed` first. Before the suites run, their setup loads each page they visit once, one at a time, so a cold `next dev` compiles every page before the parallel tests open them. Each test signs in as a member it creates and deletes with everything it wrote. A test that sends email runs only when its project is named, `pnpm test:e2e --project=email`, and sends it to Resend's test inbox, which still counts against the 100 a day; none spends AI credit, and an import's review starts from a draft the suite stores itself. Each run's results land in `test-results/`, which git ignores: Vitest's failure screenshots and its report, one HTML file at `test-results/vitest/report/index.html`, and Playwright's traces and report, which opens with `pnpm exec playwright show-report test-results/playwright/report`. Each runner empties its own folder as a run starts. CI uploads Vitest's folder when its tests fail. A headed run (`--headed`) needs the full Chromium, `pnpm exec playwright install chromium`.

Product policy (the limits on recipes, photos, and imports, which apply when content is written, the lifetimes, the import models, page size, and the time zone) lives in [`src/lib/settings.ts`](src/lib/settings.ts), each value beside its reason. `next.config.ts` checks the values against their safe ranges in [`src/lib/settings-schema.ts`](src/lib/settings-schema.ts), so a bad edit fails `pnpm dev`, `pnpm test`, and `pnpm build`.

The design reference at [localhost:3000/design](http://localhost:3000/design) shows every design token, UI primitive, and composition. It exists in development and on preview deployments only. Add primitives with `pnpm shadcn add <name>`, then run `pnpm format` and `pnpm exec eslint . --fix`.

## Database

Local development uses the Neon branch `develop`, whose connection strings are Development-scoped variables in Vercel, so `vercel env pull` never points a local checkout at production. Its images live in a Blob store of its own, `recipe-hub-images-dev`, connected to Development only. Run `pnpm db:seed` to fill the branch and the store with the synthetic sample recipes and their photos, added by a "Sample contributor" member; it skips recipes already there but uploads any of their photos the store is missing, so running it again repopulates an emptied store. Recipes `develop` copied from production name production's photos, which that store does not hold, so they show without them. `pnpm db:bootstrap` makes the owner, the account at `ADMIN_EMAIL`, an admin, creating it if needed. Change the schema in `src/infrastructure/db/schema.ts`, run `pnpm db:generate --name <change>`, and commit the generated migration. Extensions, functions, and text search configurations go in a custom migration (`pnpm db:generate --custom --name <change>`) with a `--> statement-breakpoint` after every statement. Keep migrations backward compatible (add first, remove in a later deployment), because each deployment's build applies them before the new code goes live.

## Deployment

Vercel deploys `main` to production and every push to any other branch to a preview URL, with or without a pull request. Each preview gets its own Neon branch, `preview/<git-branch>`, which the build migrates, bootstraps, and seeds before `next build` (`vercel.json`), and the Neon integration deletes it with the branch's last preview deployment. Closing a pull request or deleting a branch deletes the branch's previews, and a daily run deletes those of a branch gone from GitHub or whose newest preview is over 7 days old; a later push to the branch builds a fresh preview and Neon branch (the runbook's "Previews after a branch closes"). Production builds skip the seed. On a preview, sign in with an email code as `ADMIN_EMAIL`; passkeys made on production do not work there. Images live in three private Blob stores, one per environment, each connected to its environment alone as `BLOB_STORE_ID` and `BLOB_WEBHOOK_PUBLIC_KEY`: `recipe-hub-images-prod` for production, `recipe-hub-images-preview` for every preview, and `recipe-hub-images-dev` for local development (as Database describes). Images go under `dish/<environment>/` and `scan/<environment>/`, where a preview's environment is `preview/` and its branch's folder name (`branchFolder` in `src/lib/branch-folder.ts`), and the app authenticates to its store with Vercel's OIDC token. A preview's store holds the preview's uploads and the seed's sample photos (`dish/seed/`). A preview fetches the production photos and scans its copied database names from production's public image route and serves them through its own, so image URLs, the image optimizer, and the CDN's caching work as on production without the preview holding production's store credentials. A preview's images leave with its branch: the Preview cleanup workflow deletes the branch's folders in the preview store along with its previews, and daily any folder whose branch has no preview, with the repository secret `PREVIEW_BLOB_TOKEN`, the preview store's read-write token. Removed images move to `trash/` and are deleted for good once they outlive the removed-image lifetime. An image sweep covers the deployment's own folders: it moves uploads nothing has named within the unused-upload lifetime to `trash/`, restores any removed image a recipe or draft names again, and deletes the trash past its lifetime. No deployment deletes another environment's images. The settings file's `retention` group sets the two image lifetimes. Production runs its time-based cleanup once a day: a Vercel cron (`vercel.json`) calls `/api/cron/cleanup` at 09:00 UTC with `CRON_SECRET`, a Production variable its build requires, as the bearer token, and the route settles interrupted imports, clears expired import drafts, deletes expired saved drafts, sessions, and verifications, deletes each unused invite one invite lifetime after it expired or was revoked, and then sweeps. Vercel runs crons only on production, and the route answers 404 everywhere else, so previews and the dev server sweep after each recipe or import write instead and leave expired rows in place, which every reader ignores. On every deployment, an edit or delete removes the photos it let go once its response is sent. Vercel WAF rate-limit rules on `/search` and on posts to `/request-access` keep uncached searches from running up Neon's compute and the request form from being flooded. GitHub Actions runs lint, format, typecheck, and tests on pull requests and `main`. Every response carries a static Content Security Policy and security headers from `next.config.ts`.

## Accounts

Anyone can request access at `/request-access`. Admins review requests at `/admin`, where approving one creates a single-use invite link that expires after the settings file's invite lifetime, emailed or copied to send by text. Accepting an invite confirms an email address with a code and creates the account; members then sign in with a passkey or an emailed code, and add passkeys on `/account`. The account at `ADMIN_EMAIL` is the owner: every build's bootstrap step makes it an admin, creating it if needed, and no one can remove it or take its admin role. Changing `ADMIN_EMAIL` moves ownership to the account at the new address on the next build; the previous owner stays an admin until another admin removes that role. Admins can make other members admins, or remove a member, on `/admin`. A removed member comes back only by a new invite to their address, which creates a new account; the recipes they added stay credited to the removed account's name, and admins can still edit them.

## Imports

Members import a recipe at `/contribute` from a link or from photos of a written or printed recipe. A link's schema.org data is read when it is complete; otherwise, and for photos, a model reads the page or photos through the AI Gateway. Each import becomes a draft that the member reviews in the recipe form at `/contribute/imports/<id>` before saving. The settings file names the models and sets how long drafts are kept and how many imports a member can start a day; the Gateway's credit limit pauses imports when it is reached. `pnpm evaluate` reruns the model comparison on the public-domain cases in `scripts/evaluate/`.

## Runbook

**Logs.** In Vercel, open the project's Logs, choose Production, and filter by level. Vercel keeps runtime logs for one day and nothing alerts, so look soon after anything seems wrong. Each line is JSON with ids and codes, never emails or recipe text. Lines worth knowing: "Cleanup finished" (each daily cleanup's counts by step, with "failed" for a step that failed), "Cleanup step failed" (error: the step and its error; the next day's run does that step's work), "Images swept" (each image sweep's counts, with `failedImages`, the images a step could not move and why, and `unpurgedImages`, moved images whose CDN purge failed or did not finish within its 20 seconds; an image whose delete failed after its copy is in `failedImages` and is purged as a moved one is, since it may have moved), "Image sweep step failed" (warn: a step that failed or that the image move's 60-second bound stopped; the next sweep finds the same images again), "Recipe images could not be removed" (an edit's or delete's photos that its background task could not remove after the response, left for a later sweep, as when a running sweep held the image lock too long), "Import failed" (warn when the model failed or credits ran out, error when unexpected), "Better Auth request failed", "Header session read failed", "Sign-in code email failed", and "Sign-in code request refused as automated" (BotID). Many failures inside a page still answer 200, so read the lines, not the status codes.

**The image sweep.** On production it runs once a day, as the last step of the cleanup cron. On a preview or the dev server it runs after every recipe create, edit, or delete and every import, once the response is sent, in the deployment that took the write. After an edit or delete, on every deployment, a background task first waits for the image lock and removes the photos the write let go that nothing else names ("Recipe images removed"); on a preview or the dev server it then sweeps without letting go of the lock. Each sweep writes one "Images swept" line with what it restored, deleted, and removed, and each image it failed on: find it in Vercel's runtime logs (Logs, choose the deployment's environment, and search for the message) or in the dev server's output. "Image sweep skipped while another image move runs" means a sweep already running covers it, or an edit's or delete's task is removing photos; production's cleanup reports the sweep as "skipped", and the next day's run sweeps. "Image sweep failed" (error), or on production "Cleanup step failed" with the step `imageSweep`, leaves the work for the next sweep. To run one now on production, run the whole cleanup from the production deployment's page in Vercel or with `vercel crons run /api/cron/cleanup`; on a preview or the dev server, save any recipe, unchanged if you like. An image listed in `unpurgedImages` may be in the trash and still cached, and no later sweep purges an image once it is in the trash: purge it by hand with `vercel cache dangerously-delete --tag image:<pathname> --yes` and `vercel cache dangerously-delete --srcimg /api/images/<pathname> --yes`.

**Getting a deleted recipe back.** Neon keeps a 7-day restore window and daily snapshots for 35 days; removed photos and scans stay in Blob's trash for the removed-image lifetime, which the settings file keeps past those snapshots.

1. In the Neon console, open Backup & restore for the production branch, `main`, choose a time before the delete (or a snapshot, with One-step restore), and confirm Restore. It replaces the branch's data in place, keeping the connection string, and saves the previous state as a backup branch (`main_old_<timestamp>`), so first note any recipes added after that time, and delete the backup branch once you are sure, since each branch past ten is billed.
2. Run the image sweep now (above): on production, run the cleanup cron. It moves back every trashed image a restored recipe names, and its "Images swept" line lists them as restored.
3. Open the recipe: its photos show again.

Rehearse it on `develop`: delete a recipe with a photo on the dev server, restore `develop` in Neon to before the delete, save any recipe on the dev server, and reload the restored one.

**Previews after a branch closes.** Closing a pull request or deleting a branch runs the Preview cleanup workflow (`.github/workflows/preview-cleanup.yml`), which removes the branch's whole preview in two jobs, each holding one secret. The first deletes the branch's previews through Vercel's REST API with the project-scoped token in the repository secret `VERCEL_TOKEN`; once a branch's last preview is gone, the Neon integration deletes its Neon branch, `preview/<branch>`. The second checks out the repository, installs the packages `pnpm-lock.yaml` pins without running their install scripts, and runs `scripts/preview-cleanup/`, which deletes the branch's image folders in the preview store, `recipe-hub-images-preview` (its folder under `dish/preview/` and `scan/preview/`, and their `trash/` copies), with the store's read-write token in the repository secret `PREVIEW_BLOB_TOKEN`. It matches a folder by the whole name `branchFolder` (`src/lib/branch-folder.ts`) gives the branch, and never touches the seed's photos under `dish/seed/`. A branch's folders go only once every one of its previews is gone, and a folder written to since the first job listed the previews, as by a push right after the pull request closed, waits for the next run. The workflow also runs daily, and on demand from the repository's Actions tab (Preview cleanup, then Run workflow): it deletes every preview of a branch gone from GitHub or whose newest preview is over 7 days old (`PREVIEW_IDLE_DAYS` in the workflow), open pull request or not, then every preview-store folder whose branch has no preview left, which also covers a missed event and previews Vercel's retention removed. It logs each branch it keeps or clears with its newest preview's age, and each folder it keeps or clears with its reason and how many images it deleted. It never deletes a Git branch, and a later push to a swept branch builds a fresh preview and Neon branch. Vercel's retention, 7 days for previews, also removes a live branch's older previews, though Pro always keeps the 20 newest ready previews and the 10 newest deployments. A run that could not delete a preview or a folder fails with an error naming it, and a branch whose preview it could not delete keeps its folders until a later run finds the branch without previews; without `PREVIEW_BLOB_TOKEN` the previews still go and the images job fails, and the next run after the secret is set deletes the folders. Rerun a failed run from the Actions tab, or clear the branch's previews by hand: list them with `vercel list --environment preview -m githubCommitRef=<branch>` and delete them with `vercel remove <url> <url> --yes`, each URL its own argument (or under Deployments in Vercel); the next run then deletes the branch's folders. Neon's plan includes ten branches before each extra one is billed.

**Removing someone.** On `/admin`, "Remove member" signs them out everywhere, deletes their passkeys, and frees their address, revoking any open invite to it. Their recipes stay, under their name. To let them back in, invite their address again; accepting creates a new account. The owner's account, at `ADMIN_EMAIL`, cannot be removed.

**Imports paused.** Members see "Imports are paused" when the AI Gateway's credits run out or the monthly auto-reload cap is reached. Check the team's AI Gateway page in Vercel and add credits or wait for the next month.

**Rate limits and firewall.** Vercel WAF rules limit `/search` (100 requests a minute per IP) and posts to `/request-access` (5 per 10 minutes per IP). A third, "Log image cache bypasses", only logs requests to `/api/images/` that carry `_vercel_system`: the image route accepts that query parameter because Vercel's image optimizer adds it, so such a request skips the CDN cache. The firewall's traffic view shows blocked and logged requests.
